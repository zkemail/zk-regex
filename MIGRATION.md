# Migrating from zk-regex 2.x to 3.x

zk-regex 3.x replaces the DFA compiler with an NFA compiler. It adds real capture groups and a
Noir backend, and it produces much smaller circuits. The price is that **every public interface
changed**: the Circom template signature, how you build witnesses, the decomposed-regex JSON, the
CLI, and the Rust and JavaScript APIs.

Nothing forces you to move. The 2.x line lives on the
[`release/2.x`](https://github.com/zkemail/zk-regex/tree/release/2.x) branch, published versions
stay on npm, and critical fixes still ship there. Circuits generated by 2.x and 3.x can coexist in
one project as long as each is fed the inputs it expects. They cannot share proving keys: moving a
circuit to 3.x means a new trusted setup (Groth16) or new verification key.

| If you use | Stay on 2.x with | Move to 3.x with |
| --- | --- | --- |
| npm `@zk-email/zk-regex-circom` | `^2.3.2` | `^3.0.0` |
| npm `@zk-email/zk-regex-compiler` | `^2.3.2` | `^3.0.0` |
| npm `@zk-email/zk-regex-apis` | `^2.3.2` | removed, see [zk-regex-apis](#zk-regex-apis-is-gone) |
| Rust crates from git | `tag = "2.3.2"` or `branch = "release/2.x"` | `tag = "3.0.0"` |
| Noir `zkregex` | not available | `tag = "3.0.0", directory = "noir"` |

> If a `Cargo.toml` points at this repository with no `tag`, `rev` or `branch`, it tracks `main`
> and will break the next time it is re-resolved. Pin it.

## 1. Circom template interface

### Before (2.x)

```circom
include "@zk-email/zk-regex-circom/circuits/common/from_all_regex.circom";

// template FromAllRegex(msg_bytes)
//   signal input  msg[msg_bytes];
//   signal output out;                 // number of matches
//   signal output reveal0[msg_bytes];  // msg masked down to the public part

signal (fromMatch, fromReveal[maxHeaderBytes]) <== FromAllRegex(maxHeaderBytes)(header);
fromMatch === 1;
signal from[maxFromBytes] <== SelectRegexReveal(maxHeaderBytes, maxFromBytes)(fromReveal, fromIndex);
```

The circuit scanned the whole input by itself. The only thing the prover supplied besides the
message was the index used by `SelectRegexReveal`.

### After (3.x)

```circom
include "@zk-email/zk-regex-circom/circuits/common/from_all_regex.circom";

// template FromAllRegex(maxHaystackBytes, maxMatchBytes)
//   signal input  inHaystack[maxHaystackBytes];
//   signal input  matchStart;                       // where the match begins in the haystack
//   signal input  matchLength;                      // how many bytes the match spans
//   signal input  currStates[maxMatchBytes];        // NFA path taken by the match
//   signal input  nextStates[maxMatchBytes];
//   signal input  captureGroup1Id[maxMatchBytes];   // one pair per capture group
//   signal input  captureGroup1Start[maxMatchBytes];
//   signal input  captureGroupStartIndices[1];      // one entry per capture group
//   signal output isValid;
//   signal output capture1[64];                     // one output per capture group

component fromRegex = FromAllRegex(maxHeaderBytes, maxMatchBytes);
fromRegex.inHaystack <== header;
fromRegex.matchStart <== fromMatchStart;
fromRegex.matchLength <== fromMatchLength;
fromRegex.currStates <== fromCurrStates;
fromRegex.nextStates <== fromNextStates;
fromRegex.captureGroup1Id <== fromCaptureGroup1Id;
fromRegex.captureGroup1Start <== fromCaptureGroup1Start;
fromRegex.captureGroupStartIndices <== fromCaptureGroupStartIndices;
fromRegex.isValid === 1;
signal from[64] <== fromRegex.capture1;
```

What changed, and what to watch for:

- **Two size parameters.** `maxHaystackBytes` is the old `msg_bytes`. `maxMatchBytes` bounds the
  length of a single match and drives most of the constraint count, so keep it as small as your
  data allows. It must be at least as large as the widest capture.
- **The prover supplies the match.** The circuit no longer searches. It verifies that the path
  in `currStates` / `nextStates` is a valid run of the automaton over
  `inHaystack[matchStart .. matchStart + matchLength]` that ends in an accept state. See
  [section 2](#2-witness-generation) for how to produce those inputs.
- **`out` became `isValid`.** It is `1` for a valid match and `0` otherwise, never a count. You
  must still constrain it (`isValid === 1`). The template does not do that for you.
- **`revealN` became `captureN`.** A capture is already shifted to index 0 and zero padded, with
  the width declared in the regex definition. `SelectRegexReveal` and a separate reveal index are
  no longer needed. Capture numbering starts at 1.
- **Match position is now a witness.** 2.x templates matched anywhere in the input and patterns
  such as `(\r\n|^)from:` anchored themselves. That still holds, but `matchStart` is chosen by the
  prover, so if the position matters to your application you have to constrain it yourself.
- **Includes.** Generated circuits now include `@zk-email/circuits/utils/array.circom` and
  `utils/regex.circom`, so `@zk-email/circuits` (`6.4.1-alpha.0` or newer) has to be resolvable from your
  include path. `regex_helpers.circom` requires Circom 2.1.9 and no longer provides `MultiNOR`
  or `ORAnd`. If your own circuits used those helpers, copy them from the 2.x package.

## 2. Witness generation

In 2.x the only regex-related input was the message bytes, plus indices you usually got from
`@zk-email/zk-regex-apis` (`extractSubstrIdxes` and friends). In 3.x you ask the compiler for the
whole input set, using the graph JSON that is emitted next to every circuit.

JavaScript or TypeScript:

```ts
import { genCircuitInputs, ProvingFramework } from "@zk-email/zk-regex-compiler";
import graph from "@zk-email/zk-regex-circom/circuits/common/from_all_graph.json";

const { type, captureGroupIds, captureGroupStarts, ...inputs } = JSON.parse(
    genCircuitInputs(
        JSON.stringify(graph),
        header,            // the haystack, as a string
        maxHaystackBytes,  // MUST equal the template parameter
        maxMatchBytes,     // MUST equal the template parameter
        ProvingFramework.Circom,
    ),
);

// The helper returns capture data as arrays of arrays. The circuit wants one signal per group.
captureGroupIds.forEach((ids, i) => (inputs[`captureGroup${i + 1}Id`] = ids));
captureGroupStarts.forEach((starts, i) => (inputs[`captureGroup${i + 1}Start`] = starts));
// inputs now holds inHaystack, matchStart, matchLength, currStates, nextStates,
// captureGroupStartIndices and the per-group arrays.
```

Rust:

```rust
use zk_regex_compiler::{gen_circuit_inputs, NFAGraph, ProvingFramework};

let graph: NFAGraph = serde_json::from_str(&graph_json)?;
let inputs = gen_circuit_inputs(&graph, &header, max_haystack_len, max_match_len, ProvingFramework::Circom)?;
```

CLI:

```sh
zk-regex generate-circuit-input -g from_all_graph.json -i "$HEADER" -l 1024 -m 64 -o input.json -p circom
```

If several regexes run over the same haystack in one circuit, generate inputs once per regex and
prefix the signal names yourself.

A length mismatch between the values passed here and the template parameters shows up as
`Not enough values for input signal` at witness generation.

## 3. Bundled circuits

| 2.x template | 3.x | Notes |
| --- | --- | --- |
| `BodyHashRegex` | `BodyHashRegex` | `capture1[44]` is the base64 body hash |
| `FromAllRegex` | `FromAllRegex` | `capture1[64]` |
| `ToAllRegex` | `ToAllRegex` | `capture1[64]` |
| `SubjectAllRegex` | `SubjectAllRegex` | `capture1[64]` |
| `MessageIdRegex` | `MessageIdRegex` | `capture1[128]` |
| `EmailDomainRegex` | `EmailDomainRegex` | `capture1[128]` |
| `ReversedBracketRegex` | `ReversedBracketRegex` | `capture1[64]` |
| `EmailAddrRegex` | `EmailAddrRegex`, **different regex** | 2.x matched a bare address anywhere. 3.x matches a whole `to:` header line and captures the address. For a bare address use `EmailBasicRegex` (no capture) or compile your own pattern. |
| `FromAddrRegex` | removed | It was a hand-written composition. Use `FromAllRegex`, then run an address pattern over `capture1`, or compile `(?:\r\n|^)from:(?:[^<]+<)?(ADDRESS)>?\r\n` as one decomposed regex the way `email_addr.json` does for `to:`. |
| `ToAddrRegex` | removed | The new `EmailAddrRegex` is the direct replacement. |
| `EmailAddrWithNameRegex`, `ReversedEmailAddrWithNameRegex` | removed | Only used by the two compositions above. |
| `TimestampRegex` | not bundled for Circom | The definition ships for Noir in `noir/common/timestamp.json`. Generate the Circom version with `zk-regex decomposed -d noir/common/timestamp.json -o ./out -t Timestamp -p circom`. |

`EmailDomainRegex` keeps the limitation documented in 2.x: the domain class contains `@`, so for
`alice@gmail.com@dummy.com` the capture is `gmail.com@dummy.com`. The real domain is always part
of the capture.

Bundled captures have a fixed maximum width, shown above. If you need a different one, recompile
the pattern with your own `PublicPattern` width.

## 4. Decomposed regex JSON

```jsonc
// 2.x
{ "parts": [
    { "is_public": false, "regex_def": "(\r\n|^)from:" },
    { "is_public": true,  "regex_def": "[^\r\n]+" },
    { "is_public": false, "regex_def": "\r\n" }
] }

// 3.x
{ "parts": [
    { "Pattern": "(?:\r\n|^)from:" },
    { "PublicPattern": ["[^\r\n]+", 64] },
    { "Pattern": "\r\n" }
] }
```

- `is_public: false` becomes `Pattern`. `is_public: true` becomes `PublicPattern` with a required
  maximum byte length, which is the width of the matching `captureN` output.
- Each `PublicPattern` becomes a capture group. **Groups inside your own patterns must therefore
  be non-capturing**: write `(?:a|b)`, not `(a|b)`. A stray capturing group shifts every
  capture index after it.
- Patterns are parsed by the Rust `regex-syntax` crate. `\w`, `\d`, `\s` and `.` are Unicode
  aware there and expand to hundreds of states. Prefer explicit ASCII classes such as
  `[a-zA-Z0-9_]`. The Noir backend rejects automata that grow past what its transition table can
  encode without ambiguity (about 257 states).
- Lookarounds and backreferences are not supported, same as 2.x.

## 5. CLI

| 2.x | 3.x |
| --- | --- |
| `zk-regex decomposed -d def.json -c out.circom -t NameRegex -g true` | `zk-regex decomposed -d def.json -o ./out_dir -t Name -p circom` |
| `zk-regex raw -r 'REGEX' -s substrs.json -c out.circom -t NameRegex -g true` | `zk-regex raw -r 'REGEX' -o ./out_dir -t Name -p circom` |
| none | `zk-regex generate-circuit-input -g graph.json -i INPUT -l MAX_HAYSTACK -m MAX_MATCH -o input.json -p circom` |

- `-c <file>` became `-o <directory>`. The compiler writes `<name>_regex.circom` (or `.nr`) and
  `<name>_graph.json` there. Keep the graph: witness generation needs it.
- `-t` takes the PascalCase base name and the compiler appends `Regex`. `-t Timestamp` yields
  `template TimestampRegex` in `timestamp_regex.circom`. Passing `TimestampRegex` yields
  `TimestampRegexRegex`.
- `-p circom|noir` is required.
- `-g` (generate substrings) and `-s` (substring transition JSON) are gone. With `raw`, mark the
  public parts with ordinary capture groups in the regex itself.
- The halo2 output (`-h`) is gone.

## 6. Library APIs

Rust, crate `zk-regex-compiler`:

| 2.x | 3.x |
| --- | --- |
| `gen_from_decomposed(path, halo2_dir, circom_path, template_name, gen_substrs)` writes files | `gen_from_decomposed(config: DecomposedRegexConfig, template_name: &str, framework: ProvingFramework) -> CompilerResult<(NFAGraph, String)>` returns the graph and the code |
| `gen_from_raw(regex, substrs_path, halo2_dir, circom_path, template_name, gen_substrs)` | `gen_from_raw(pattern, max_bytes: Option<Vec<usize>>, template_name, framework)` |
| none | `compile(pattern) -> NFAGraph`, `gen_circuit_inputs(&graph, input, max_haystack_len, max_match_len, framework)` |
| `DecomposedRegexConfig { parts: Vec<RegexPartConfig { is_public, regex_def }> }` | `DecomposedRegexConfig { parts: Vec<RegexPart> }` with `RegexPart::Pattern(String)` and `RegexPart::PublicPattern((String, usize))` |

JavaScript, package `@zk-email/zk-regex-compiler` (wasm): `genFromDecomposed(json, templateName,
framework)` and `genFromRaw(regex, maxBytes, templateName, framework)` now return
`{ code, graph }` instead of a code string, and `genCircuitInputs(...)` is new. `framework` is the
exported `ProvingFramework` enum.

### `zk-regex-apis` is gone

The crate and npm package `zk-regex-apis` (`extract_substr_idxes`, `extract_from_addr_idxes`,
`pad_string`, ...) are not part of 3.x. They located reveals for the 2.x circuits, a job that
`gen_circuit_inputs` now does. If you still need plain substring extraction off-circuit:

- keep depending on the 2.x crate (`tag = "2.3.2"`), which works independently of the compiler
  version you use, or
- copy the two small modules into your project, as
  [`relayer-utils`](https://github.com/zkemail/relayer-utils/tree/feat/new-compiler/src/regex) did.

## 7. Noir

Noir support is new in 3.x, so there is nothing to migrate from. Depend on the library and the
compiler from the **same tag**, because generated code and the library's transition encoding have
to agree:

```toml
zkregex = { tag = "3.0.0", git = "https://github.com/zkemail/zk-regex", directory = "noir" }
```

Projects pinned to the pre-release tag `2.2.0` should regenerate their circuits when they move
to 3.x. Capture handling changed after that tag (single-byte captures were extracted
incorrectly), so library and generated code from different sides of that change do not mix.

## 8. Checklist

1. Pin whatever you are not migrating yet (see the table at the top).
2. Rewrite decomposed JSON files. Make inner groups non-capturing and add capture widths.
3. Regenerate circuits with the 3.x CLI and keep the `_graph.json` files.
4. Update template instantiation: two parameters, new inputs, `isValid === 1`, `captureN`.
5. Replace reveal-index helpers with `genCircuitInputs` in your input generation.
6. Replace uses of `FromAddrRegex`, `ToAddrRegex`, `TimestampRegex`, and check whether the new
   `EmailAddrRegex` still means what you need.
7. Recompile, run a new setup, and redeploy verifiers. Old proofs do not verify against new keys.
